# Automatic GHL processing after statement imports

GHL setup includes an account-controlled Automatic GHL updates after statement imports setting. Enabled connections queue one private job for each newly imported statement credited to the active mapped owner or agent. Existing statements are not retroactively queued. Manual carrier collection through Sync now is unchanged. Personal/shared locations continue using the same verified sub-account and user assignment; each producer processes only statement entries credited to their own ComFlow account and contacts assigned to their mapped GHL User ID. Shared team imports queue separate jobs for each enabled credited producer. Agents manage only their own processing setting; agency tokens and teammate assignments remain owner-managed.

Migration 0017 queues work inside the same transaction that marks a statement imported, after its carrier rows exist. Uploads, previews, failed/rolled-back imports, repeated imported status, and disabled connections do not generate duplicate work. Corrected statements get their own job; superseded sources cannot be processed. The queue stores operational IDs, timestamps, numeric summaries and safe error codes, never credentials, contact names or MBIs.

The existing carrier worker can consume the queue. A dedicated worker (`npm run ghl:start` from worker/) handles only automatic GHL jobs and never opens a carrier portal. It runs without an open web page or user login cookie. A trusted server-only async context is bound to a claimed import job and its active lease; it rechecks the current active producer, agency, credited imported source, enabled setting, location and GHL user mapping before granting background repository access. Browser requests cannot set this context. Contexts are isolated between jobs and expire on completion, revocation or lease expiry.

Processing is scoped to policies affected by that import. It verifies original source hashes/rows, links existing contacts, creates missing contacts after complete duplicate checks, recovers uncertain contact/field operations, applies eligible SunFire-supported plan details, rechecks Active proposals, and applies eligible statement-only Active updates. Existing identity, newer-policy, multiple-application, chargeback, no-commission-expected and field-mapping guards remain in force. Unsupported/missing fields stay unchanged. This does not add new inference rules or send marketing messages. Previously confirmed name exceptions remain bound to their exact evidence.

The existing durable creation and note/field journals remain the source of truth for retries. History is saved before fields change. A lost contact/note/field response is reconciled before another write; unknown note POSTs are not blindly replayed. Jobs for one owner/connection cannot run concurrently. Progress counters survive retries. Failed jobs retry after five minutes, with a maximum of three attempts before Needs attention. The account holder can explicitly verify/resume a held technical job from GHL setup. Matching holds are reported separately and do not block the statement import.

GHL note creation and field updates are not one atomic provider transaction, and an outside concurrent edit between a fresh check and a write cannot be completely prevented. Settings can stop later operations, but cannot undo an API request already in flight. Turning automation off never deletes previously saved contacts, notes or links.

Validation: pure pipeline ordering/scope/failure tests; background-context lease/revocation/isolation checks; worker tests and type checks; rollback-only isolated SQL trigger/claim/serialization tests; and `scripts/ghl-import-automation-drill.ts`, which uses the real import RPC, source parser/storage, queue consumer, access context and durable journals against an isolated database. Every HighLevel request is intercepted in that drill. It verifies contact link/create, history-before-Active, a lost successful PUT response, retry without duplicates, repeat import rejection, and corrected import without duplicate CRM records. Real GHL requests in that rehearsal: zero.

Run the drill only with GHL_AUTOMATION_SYNTHETIC_ONLY=true and an isolated Supabase status env file whose API_URL is http://127.0.0.1:55431. It refuses other databases/destinations and cleans up only its own fictional fixture agency. Private environment files and logs stay outside Git. Local setup must apply the migration and keep a GHL worker running; durable jobs wait safely while the worker is stopped. Deployment/startup service installation is separate from this review-branch local preview. Main and hosted databases are not changed.

Migration 0018 extends the same rules to agents. Agent evidence queries explicitly filter user_id even in trusted background jobs. Contact journals and statement policy operations recheck the active credited producer, original source hash and current mapping in the database. SunFire plan-detail updates additionally require the current explicit application assignment; enrollment ownership alone is not reassigned. A contact already owned by another GHL user is never reassigned or duplicated automatically. Two enabled agents in one shared location are exercised end-to-end in scripts/ghl-agent-isolation-drill.ts; supabase/tests/ghl_agent_imports.sql tests a shared statement, cross-agent/cross-agency denials, changed mappings and disabled accounts.
